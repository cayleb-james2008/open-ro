# Bar — OpenRO scale-up (ultra loop, project run)

Kind: code + interface (a local web app: a Rust binary serving an embedded chat UI, driving
Roblox Studio through an MCP bridge over stdio).
Delivered = commits on branch `loop/work` in this repo. Nothing is pushed or published by this run.
Facts never to invent: live-model behaviour (the OpenCode Go key is NOT available in this
environment; the live path is real code proven against a stub, stated as such), real-Studio
behaviour (no Studio exists on this machine; the bridge is proven against the mock fixture and
the real Studio MCP server is a drop-in value of OPENRO_MCP_COMMAND — claims must say exactly
that), published games, user counts.

Owner brief (the goal, approved — do not drift it): OPENRO — you describe the game, it builds
it. A proactive creative agent in a plain chat window, full access by default, that can
one-shot a game.

Conditions:

- C1 (cmd): `bash .loop/verify <label>` passes: cargo build clean and the full test suite green.
- C2 (cmd): A real skill system: at least four game-building skills, each defined by a Rune
  script in a registry with a name and description; the agent's system prompt is generated
  from the registry (a test asserts every registered skill appears in the prompt); each
  skill's Luau is produced by executing its Rune script and varies with its parameters.
- C3 (cmd): Place-tree awareness including instances: the bridge tree carries scripts AND
  instances; the agent can create and delete instances through the bridge (class, name,
  parent, properties); checkpoint + revert covers instances as well as scripts (proven
  against the mock fixture).
- C4 (cmd): Multi-script ask: one ask writes two different scripts generated by two different
  skills; both land in the tree with their own generated content; revert removes both.
- C5 (cmd): A stronger repair loop: (a) a stub model that repeats the failing generation once
  before fixing it still converges to a passing playtest, and the transcript records the
  repair attempts; (b) a stub model that never fixes the game ends in an honest failure that
  names the actual console output, after a bounded number of failed playtests — never a hang,
  never a false success.
- C6 (cmd): Bridge capability awareness: the client fetches the server's tool list at
  connect; if the connected server lacks a tool the agent needs, the ask refuses honestly
  naming the missing tool (proven against a minimal-tools mock fixture). The README documents
  the real Roblox Studio MCP server as the drop-in value of OPENRO_MCP_COMMAND.
- C7 (cmd): Persistence: chats and their thread lines survive a server restart (data dir on
  disk); multiple named chats can be created and switched between.
- C8 (cmd): Honest states preserved (baseline behaviour, must not regress): no key → chat
  refuses honestly; no Studio → the chip says not connected and asks refuse honestly;
  nothing is fabricated in either case.
- C9 (cmd): Themes: the served page carries light and dark theme definitions with dark as
  the default, and a settings toggle that persists the choice.
- C10 (judge): The rendered UI reads as a familiar, quiet chat window in OpenRO's own words,
  with no AI-slop signs (no hue gradients, glows, gradient text, emoji icons, hype copy).
  Example that should pass: this shell — sidebar with the game's chats, one thread, the
  "Describe the game…" composer, the Studio chip. Example that should fail: the same layout
  with a purple-blue gradient, a sparkle icon and "Unleash your creativity" — it would fit
  any product.
- C11 (owner): The owner grades the rendered UI's look. The loop never marks this passed.
- C12 (cmd): Replacement staging exists at ~/workspace/restart-20261117/replacement/openro/:
  README.md, the résumé-site project page (HTML, in the current site's style) and CLAIMS.md,
  with every factual claim tied to a proof in this repo.

## DIRECTION v1 (interface)

- Product: OpenRO — you describe the game in plain words; it builds the game in your Studio
  place and proves it with a playtest.
- Character: eager, plain-spoken, game-dev native.
- World: the Studio workbench at night — a dark bench, tools laid out, one accent (the
  incumbent blue #2f6fed stays). Dark is the default because the work happens in Studio
  after hours; light is fully supported.
- Moments: the playtest verdict in the thread — passed or failed, with the console text —
  is the one moment that gets weight and colour.
- Signature: every change set is reversible. The Revert control is always present, and the
  thread narrates the build in plain words ("Wrote …", "Playtest passed.").
