# Set-up (first run of a project)

Set-up makes the first change safe to judge. Keep it short: no check for every requirement, no helpers, no deep study of the code. On a small project `verify` may be a few lines around the existing test command, and you probe only the host features you are about to use.

1. **State file first.** Create `.loop/STATE.md` with `status: setup` and `next: set-up step 2`, and copy the owner's inputs word for word into its "Owner brief" block. Update the `next:` line after each step, so that a run that dies here can be resumed.
2. **Target.** Confirm what actually runs or ships by following the build or entry point. If something here is live, or others are changing the tree, follow `live.md` before anything else and say so under "Needs from you". The run then happens in the frozen copy that `live.md` makes: every later step here, and every commit, means that copy and never the live tree.
3. **Starting point.** With no version control, start a local repository (`git init`); if that is impossible, `hosts.md` says what stands in. Switch to a new branch (`git checkout -b loop/work`), or keep a branch the project's tools already depend on and record its name in the state file. Create `.loop/.gitignore` holding three lines: `runs/`, `tmp/` and `exam/`, and an empty `.loop/ANSWERS.md`. If the tree has uncommitted work, commit it first as "as found", leaving `.loop/` and any `ULTRA-BRIEF.md` out. Tag the result `loop-baseline`. If the repository already carries that tag from another run, give this run's two tags a short prefix (`fleet2-loop-baseline`, `fleet2-loop-start`) and record it in the state file as a line `tags: fleet2-`. If git has no identity set, add `-c user.name=ultra-loop -c user.email=ultra-loop@localhost` to each commit. Building something new: the starting point is an empty commit.
4. **Host.** Find out by trying what this host can do (`hosts.md`) and record the labels.
5. **Kit and baseline.** Read each existing check and script before its first run (rule 9), and leave out any that starts, drives or writes to a real system. Write `.loop/verify`: one command, run as `bash .loop/verify <label>`, that runs every hermetic check the project already has (tests, build, lint), cheapest first, each under a timeout; finds tests by pattern, leaving out `.loop/`, so that a new test needs no change here; saves raw output and exit codes under `.loop/runs/<label>/`; prints one line with the counts and the names of failing checks; and exits non-zero when any check fails. Check scripts you write for it live in `.loop/checks/`, which is tracked. Run `bash .loop/verify baseline` once. A check that needs something you cannot reach is "not run", never passed. Where the project has no checks, give the kit a first few: for code, golden outputs of two or three main uses that you confirmed correct, with dates and ids masked; for a document, links resolve, code samples parse and numbers recompute; for a page, it loads with no console errors at a narrow and a wide width.
6. **Bar.** Write `.loop/BAR.md`, about one page: what kind of project this is (`kinds.md`); what "delivered" means (default: commits on `loop/work`); the facts you must never invent (prices, names, claims, testimonials); and numbered pass conditions C1, C2 and so on, taken from the owner's words and the project's own documents. If the owner gave no goal beyond running the loop, take the conditions from the purpose the README states, plus the cheapest floors for the kind (the page loads with no console errors at a narrow and a wide width; links resolve; the tests pass), and record that assumption under "Needs from you". Each is one sentence a stranger could check, with its source and its kind:
   - `cmd`: a command with an exit code;
   - `metric`: a number against a threshold from the documents or a reference, never from the value you just measured. With no outside threshold, record the value and make the condition `owner`;
   - `judge`: a yes-or-no question about the artifact. Its example pair, one case that should pass and one that should fail, is written when the condition is first used;
   - `owner`: only his eye or ear can tell (taste, humour, style, sound, feel). The loop never marks these passed and never counts them as work.
   
   Where the documents contradict each other, do not pick silently: put the question under "Needs from you" with the reading you assumed, and change nothing that depends on the answer. The floors in `kinds.md` and `interfaces.md` are not copied into the bar now; they are what the hunt looks for later. From here the bar is append-only: conditions may be added or tightened by a new line, and no line is edited or removed.
7. **Backlog.** Write `.loop/BACKLOG.md` as a table: id (B1, B2 and so on), what is wrong, how to reproduce it, severity, and the status in the last column. It holds every failing check and every condition you saw unmet while writing the bar. A defect list you were handed is a set of leads: a row is `open` once you have reproduced it. A row that depends on an unanswered question to the owner is `waiting`. Building something new: every condition is an `open` row, and the first one worked is the smallest version that runs end to end.
8. **Start.** Write the first ledger row, quoting the line that the baseline run printed. Commit `.loop/` in a commit of its own (`loop: set-up`) and tag it `loop-start`. Then set `status: running` and `next: phase 1` (or `next: phase 2` if no row is `open`), and commit that as `loop: start`.

## Moving a run that is under way

When the project already holds a loop's records (an older Omni-Loop run, or an Ultra Loop run from another version), do not start from zero:

- `loop-baseline` is the last state that was delivered or accepted, not the working tip. On a live system it is the commit production loads. Work that is neither landed nor accepted then shows in every reviewer's `CHANGES.diff` and in the whole-diff step of phase 3.
- The old records stay where they are, as history. Leave them out of frozen copies, as you leave out your own notes.
- Open items become backlog rows. The ones nobody has reproduced yet go in the Leads list.
