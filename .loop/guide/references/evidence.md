# Why each part of the loop exists

For whoever maintains this skill. The agent doing the work does not need this file.

Each row gives a mechanism, the strongest evidence behind it, and how strong that evidence is. "Strong" means several independent sources plus an event recorded on the owner's own machine. "Moderate" means several sources, or one measured source plus a first-party event. "Weak" means one source or an inference. The full research report, with about 180 sources and a section on where the evidence is thin, is `research/report.md` in the Ultra Loop folder. Trial results are in `TRIALS.md` there. Rows marked first-party come from the owner's own runs: the trials, and the Omni-Loop v5 run on a live system (9 and 10 November 2026), whose lessons this skill carries.

| Mechanism | Strongest evidence | Strength |
|---|---|---|
| Tag and run the starting point before any change | A frozen agent that never changed its policy still moved 5 to 12.5 points between rescorings on 40 held-out tasks ([Trace Evolution Bench](https://arxiv.org/abs/2610.15055)); RRSI accepts a change only beyond a noise band taken from the unchanged baseline ([RRSI](https://arxiv.org/abs/2609.24972)) | Strong |
| Start every change from outside evidence | Self-correction without external feedback sometimes lowers accuracy ([Huang et al.](https://arxiv.org/abs/2310.01798)); editing a harness with no reference run lowered scores, probing first raised them ([Harness²](https://arxiv.org/abs/2610.14224)) | Strong |
| See the check fail first | In the owner's lesson library, a check that could not fail is the most repeated failure (36 entries); in the first Omni-Loop run two new checks failed for the wrong reason before they tested the defect | Strong |
| Never change a check to pass; a "disputed" exit | Agents with access to tests pass impossible tasks by editing or special-casing them, and a stop-and-flag exit cut that sharply on some models ([ImpossibleBench](https://arxiv.org/abs/2510.20270)); Anthropic's harness forbids removing or editing tests ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) | Moderate; the size of the effect varies by model |
| Someone other than the maker judges the real artifact | Agents skew positive when grading their own work, and a separate evaluator that drives the running app is easier to tune ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)); an independent critic added 5.9 to 9.5 points on Terminal-Bench at 1.13 to 1.25 times the cost ([Rethinking Verification](https://arxiv.org/abs/2610.34577)) | Strong; a same-model critic in a fresh context is unmeasured |
| Reproduce a reviewer's finding before acting | Model reviewers frequently mark correct code as defective, more so when asked to explain and fix; executing the proposed fix filters most of it ([Jin and Chen](https://arxiv.org/abs/2603.00539)) | Strong |
| Review in batches; two reviewers only for risky changes | The evaluator is worth its cost when the task is beyond what the model does reliably alone, and overhead otherwise ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)); completion gates can raise cost substantially, and an independent critic gives the better trade of accuracy for cost ([Rethinking Verification](https://arxiv.org/abs/2610.34577)); `TRIALS.md` round 1 | Moderate |
| Fix known defects first, strict steps last | `TRIALS.md` round 1: a first draft that built every check before fixing anything fixed 1 of 11 planted defects in the time a plain prompt fixed all 11 | Weak as research, direct as a first-party trial |
| Size the run: most work gets the task form | `TRIALS.md` round 3, small projects: a plain prompt with one fresh check fixed 10 of 11, 36 of 38 and 17 of 17 planted defects in about 5 minutes; the full loop fixed 11 of 11, 37 of 38 and 16 of 17 in 35 to 40 minutes at three to seven times the cost. An evaluator is overhead when the task is within what the model does alone ([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)) | Moderate; one run per arm, small projects only |
| Rules a script can check are checked by a script (the loop check, the driver) | `TRIALS.md` round 3: with the rules in prose only, two of three runs broke them (an invented status, no report, several defects in one commit). Omni-Loop v5.1 shipped a controller for the same reason after its first run | First-party |
| Read a script before running it | Omni-Loop v5 run: a project script run with `--help` ignored its arguments and started a second host, which ran for 4.6 hours | First-party, one incident |
| Live systems: freeze the tree, list the writers, land and restart together, soak | Omni-Loop v5 run: the live tree changed twice during a 20-minute baseline; an outage came from files landed but not yet loaded, which an unrelated profile edit then loaded | First-party |
| A defect list handed in is a set of leads | Omni-Loop v5 run: 2 of 4 handed-in leads were wrong about the cause, and 6 of 35 inherited citations did not support what was attributed to them. This skill's own research run corrected about 290 of 1,320 delegated claims | First-party |
| Judges: a fixed question, a majority decides, at most two rounds | `TRIALS.md` round 3: one run reworded its judge prompts between rounds, added about 25 polish attempts, and deleted a required code sample to win a yes. Round 4: with the question fixed the sample was kept and repaired, but one condition was still judged four times and about 12 of 52 changes were wording polish, so the limit became two rounds and taste was named as cosmetic. Criteria drift while grading ([Who Validates the Validators](https://arxiv.org/abs/2404.12272)) | First-party plus one source |
| Helper briefs carry a budget and a list of scripts not to run | Omni-Loop v5 run: an open-ended evaluator took 53 tool calls and 1,175 seconds, part of it waiting on its own timers; with three added lines, 21 to 36 calls and 410 to 660 seconds | First-party |
| An unattended run gets its own process scope and a memory limit | Round 4 in `TRIALS.md`: three trial runs started from an agent session with `setsid` and `nohup` were killed at 01:07 on 2026-11-10, when the memory daemon killed the Claude app's whole process scope (131 processes). Both project runs continued from their state files when started again in a scope of their own | First-party, one incident |
| Moving a run that is under way; a review before every landing; a Leads list; a maker brief; real data in pictures for the owner; a tag prefix | The review written by the Omni-Loop session after it moved the live DSH fleet run onto Ultra Loop 2.0 (2026-11-10): eight findings, each from that move | First-party, one run |
| Hunts by fresh finders, one aimed at the checks | Independent review passes merged through one filter raise recall ([SWR-Bench](https://arxiv.org/abs/2509.01494)); a verifier that evolves unanchored collapses into an always-pass grader, and the task score does not show it ([Who Verifies the Verifier](https://arxiv.org/abs/2610.11464)) | Moderate; differently-aimed finders have no controlled test |
| Sealed acceptance checks the maker does not see | Self-written tests stay near-perfect while real performance falls; a fixed audit the agent can neither write nor read, returning only accept or reject, restored progress ([Guo et al.](https://arxiv.org/abs/2607.24300)) | Strong for sealing; no seal strength is measured for any agent tool, which is why the label is reported |
| Judges tested on a good and a bad example first | Graders need validating against known cases, and criteria drift while grading ([Who Validates the Validators](https://arxiv.org/abs/2404.12272)); the owner's records include a judge that failed 10 of 12 good images | Moderate |
| Owner conditions are never marked passed | The owner's records hold 11 cases where every mechanical check passed and he rejected the work | Strong, first-party |
| State in files, appended, never rewritten wholesale | Fresh sessions resume from a progress file, a feature list and git history ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); rewriting a context store erodes its detail ([ACE](https://arxiv.org/abs/2510.04618)) | Moderate |
| The ledger is the only memory; no lessons file | Lesson memory helps in its own papers and hurts in others; self-evolution from feedback raised prompt-injection success ([Appreciation Teaches Unauthorized Execution](https://arxiv.org/abs/2610.39122)) | Moderate |
| Stop on evidence, keep the last kept state | In 58 percent of settings agents improved on their first valid attempt, and improvement was inconsistent ([RSIBench-Data](https://arxiv.org/abs/2607.25886)); gains concentrate in early rounds and self-grading inflates ([iterated grading](https://arxiv.org/abs/2611.05548)) | Moderate; no study tracks a loop like this on a real project over many rounds |
| Wait for helpers in the same run; resume from the state file | `TRIALS.md` round 1: two headless runs ended mid set-up because the agent ended its turn to wait for helpers; both resumed correctly from disk. Round 4: two project runs were killed by the machine in mid-review and both continued correctly from their state files, with no lost or repeated work | First-party trials |
| Hard stops for spending, publishing and destructive actions | The owner's standing rules; vendor practice on containing unattended agents ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)) | Moderate |
| Interface order and gates | The named skills' own text (`interfaces.md`), WCAG 2.2 AA for contrast and target size, the Core Web Vitals "good" bounds for lab performance | Weak for the order; the gates are published standards |
| Every number is a default | No source gives validated thresholds for a single project; the earlier loop's weights and caps were never exercised | Moderate |
